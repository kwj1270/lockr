# Spec

새 기능의 PRD(Product Requirements Document)와 TDD Plan을 생성한다.

기존 도메인 컨텍스트와 코드베이스를 분석하고, 필요시 외부 리서치를 병행하여 실제 구현 가능한 수준의 스펙 문서를 만든다.

## 사용법

```
/spec <기능 설명>
```

## 프로세스

### 1단계: 컨텍스트 수집

기능과 관련된 정보를 병렬로 수집한다.

**프로젝트 내부:**
- `docs/domains/` 아래 관련 도메인 컨텍스트 문서를 읽는다
- 관련 도메인의 기존 코드를 탐색한다 (Domain, Service, API, Repository)
- 기존 이벤트 흐름과 도메인 간 의존관계를 파악한다
- `docs/specs/`에 유사한 기존 스펙이 있는지 확인한다

**외부 리서치 (필요한 경우):**
- 도메인 지식이 부족한 경우 WebSearch로 조사한다
- 예: "회비 관리 기능"이면 동호회 회비 운영 방식을 먼저 리서치

### 2단계: 사용자 인터뷰

수집한 컨텍스트를 바탕으로 핵심 질문을 정리하여 사용자에게 확인한다.

확인할 내용:
- **범위**: 이 기능에 포함할 것과 제외할 것
- **권한**: 누가 이 기능을 사용하는가 (역할별 권한)
- **비즈니스 규칙**: 핵심 제약 조건과 엣지 케이스
- **연쇄 효과**: 다른 도메인에 미치는 영향 (이벤트, 데이터 변경)
- **우선순위**: v1에 포함할 것과 향후로 미룰 것

질문은 조사한 내용을 기반으로 구체적으로 한다. "어떻게 할까요?"보다 "A 방식과 B 방식 중 어느 쪽이 맞나요?" 형태가 좋다. 사용자가 빠르게 결정할 수 있도록 리서치 결과와 함께 선택지를 제시한다.

### 3단계: PRD 작성

`docs/specs/<feature-name>.md`에 아래 형식으로 작성한다.
아래 PRD 템플릿 형식을 따른다.

```markdown
# PRD: [기능명]

> **Status**: Draft
> **도메인**: `domain/...`
> **최종 수정**: YYYY-MM-DD

---
```

### 4단계: TDD Plan 작성

PRD를 바탕으로 `docs/plans/<feature-name>-plan.md`에 TDD Plan을 작성한다.

```markdown
# TDD Plan: [기능명]

> **PRD**: `docs/specs/<feature-name>.md`
> **도메인**: `domain/...`
> **생성일**: YYYY-MM-DD
> **상태**: 진행 중

---

## 구현 대상

| # | 기능 | 유형 | 상태 |
|---|------|------|------|

---

## Phase 1: Domain Entity
- [ ] 테스트 설명 1
- [ ] 테스트 설명 2

## Phase 2: Application Layer
**의존**: Phase 1 완료 필요
- [ ] 테스트 설명

## Phase 3: Infrastructure Layer
**의존**: Phase 2 완료 필요
- [ ] 테스트 설명

## Phase 4: API Layer
**의존**: Phase 3 완료 필요
- [ ] 테스트 설명
```

TDD Plan 작성 원칙:
- Phase는 Domain → Application → Infrastructure → API 순서를 따른다
- 각 테스트는 "~해야 한다" 형식으로 작성한다
- 테스트 하나가 하나의 행위를 검증한다
- Phase 간 의존관계를 명시한다
- 가장 단순한 성공 케이스부터 시작하고, 예외/엣지 케이스를 뒤에 배치한다

### 5단계: 리뷰 요청

작성한 PRD와 TDD Plan을 사용자에게 보여주고 피드백을 받는다.

확인 포인트:
- 빠진 요구사항이 없는지
- 비즈니스 규칙이 정확한지
- API 설계가 적절한지
- TDD Phase 순서와 테스트 항목이 맞는지

피드백을 반영하여 문서를 수정한 후, `/go docs/plans/<feature-name>-plan.md`로 구현을 시작할 수 있음을 안내한다.
